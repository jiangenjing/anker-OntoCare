2\.1 项目阐述#

OntoCare 面向安克复杂 L3 售后，用 Service Ontology 统一业务语义、用 Decision Ontology 约束动作空间， 让 AI 从“能调用工具”升级为“能在明确业务规则边界内安全办事”——把客户问题转化为有依据的答复、可追溯的经营核查与可复用的改进策略。

立即体验 · LIVE DEMO

扫码打开 OntoCare 智能售后工作台

手机扫码即可进入真实运行环境，无需配置任何密钥。可直接体验用户端多轮对话、产品消歧、带引用答复，以及商家端邮件草稿与经营归因看板。

https://web\-production\-195cd\.up\.railway\.app/

解决什么问题

产品包含用户端与商家端，目标用户不仅包含外部消费者，也覆盖了安克内部的客服与经营管理团队。

外部 · 消费者

需要更准的答案与更快的闭环：不再答非所问、反复追问，也不必在长链路里来回拉扯。

内部 · 商家

一线客服需要快速接管复杂 Case；GTM 策略与业务管理者需要真实的全局洞察来优化流程。

做了什么

产品是双视图工作台：用户端「看懂问题、找对对象，给出有依据的下一步」，商家端「高效处理客户来信，让工单积累为经营线索」。

USER

用户端 · 看懂问题、找对对象，给出有依据的下一步

文本 / 故障图片 / 视频均可发起求助

1

##### 多模态理解与「猜你想问」：让用户更容易表达问题

用户可以通过文字、故障图片或视频发起求助。系统先将图片和视频采样画面转化为可见现象、型号线索和错误码等文字证据，再结合用户描述进行检索。每轮对话同步更新「猜你想问」和快捷选项，减少反复打字。

2

##### 主动订单关联与连续排障：让服务跟得上上下文

面对「S1 Pro 不吸了」等模糊描述，系统结合品类、订单 SKU 与对话信息区分产品，展示带图片、订单号和购买日期的候选卡片。确认后限定知识范围，保留已尝试步骤继续推进排障，并根据情绪调整沟通方式。

3

##### 带引用的答复与人工交接：让建议有依据，疑难问题有出口

回复附带来源引用和可折叠的处理摘要。遇到信息不足、产品冲突或高风险诉求时，系统提示需要补充的证据或人工复核，并整理当前上下文与处理记录，支持后续接管。

技术底色 · 双本体让业务关联与处理边界清晰可查

##### Service Ontology · 连接产品、订单、知识与证据

帮助系统确认「当前处理谁的问题、哪些资料适用」，从源头避免跨型号知识混用。

##### Decision Ontology · 计算允许与禁止的动作

结合案件状态输出 Allowed / Blocked，AI 越不了权。

##### 规则 \+ 固定工作流 \+ LLM 协同

再通过引用、关键字段及业务承诺校验，降低错误风险。

邮件辅助 · 经营看板 · 归因助手

1

##### 邮件辅助处理：从客户原文到可编辑的回复草稿

商家可以选择已有工单或粘贴邮件正文，系统结合产品、订单、物流、质保与知识生成回复草稿，支持语气调整、多版本生成及多语言翻译。引用随草稿保留，方便核对后使用。

2

##### 经营可视化看板：从统计数字下钻到原始工单

聚合全量工单快照，展示产品工单占比、咨询场景、错误码及知识覆盖情况。点击图表或归因候选，即可查看关联工单、Excel 行号和原始邮件，帮助管理者识别值得优先核查的问题。

3

##### 经营归因助手：围绕一组工单追问，形成可核查的行动建议

商家可以直接询问「这些工单有什么共同特征？」「下一步应该核查什么？」，助手读取本体关联与归因 Trace，生成附带证据链的分析建议。例如：

支持产品核查：E25、E28 的两条工单包含 3212 错误码及相似拖布阻塞描述，建议按型号分别检查维护步骤和复现条件，再决定是否提交工程调查。

优化服务流程：针对「只收到配件」等拆单咨询，建议逐件展示包裹与物流记录，并核对客户实际收到的商品。

01

本体（Ontology）路线 —— 从“牵一发而动全身”到真正的业务敏捷

现有方案痛点 · 传统 Coding \+ Skill 路线

传统的智能客服架构把规则硬编码在代码或流程里，属于「牵一发而动全身」。一旦安克新增了品类、调整了售后政策，底层代码、API 和 Prompt 全都要跟着重写，维护成本极高。

我们的创新 · 本体论降维打击

我们彻底摒弃硬编码，采用 Service Ontology \+ Decision Ontology 双本体路线，将业务实体和售后 SOP 沉淀为一张可视化的知识图谱。

💡

##### 核心价值 · 为什么这对安克重要

对于安克这种一定要越做越大的企业，多 SKU、多国家政策是常态。传统路线会让系统越改越臃肿，而我们的本体路线实现了真正的业务敏捷，让系统架构随着业务的扩张而无限延展。我们不仅保留了确定性，更赋予了系统生命力。

确定性！友好性！

可视化打消评委疑虑：演示页面将直接展示本体的可视化图谱与流程图——产品、订单、故障、政策如何通过节点与连线串联一目了然。业务变动时只需在图谱中修改节点连线或属性，完全无需改动底层代码。

02

基于红蓝对抗降噪与 Bad Case 驱动的自进化飞轮

现有方案痛点：售后场景的“致命伤”是幻觉——AI 容易自由发挥、产生不合规回答；传统 RAG 面对复杂多轮对话极易崩溃（多跳能力弱），且无法从错误中学习，普遍缺乏知识库精调与降噪的闭环机制。

STEP 01

##### 红蓝对抗

用 Persona 模拟不同性格买家（急躁型、技术型、情绪宣泄型、利益导向型等），与客服 Agent 多轮对话，收集海量、真实、带对抗性的问答数据。

STEP 02

##### Judge 评估

引入 LLM as a Judge，从事实性、安全性、相关性、合规性等维度打分；再由 Supervisor 复核，不合格的打上 Bad Case 标签并定位失败原因。

STEP 03

##### 降噪与剔除

靶向修正：检索召回了错误知识就降低权重或剔除；知识不够权威就修正 FAQ 条目；规则缺失就更新 Decision Ontology。

STEP 04

##### 人工审核回流

修正后的知识必须通过运营人员人工审核，通过后再写回知识库与 Ontology，形成完整的系统自进化闭环。

核心价值与数据：引入学术界常用于评估 Agent 稳定性的 pass^8 指标（基于 τ\-bench 基准方法），在模拟复杂售后场景的 8 轮对话测试中发现：

03

业务经营归因 —— 从“单点工单”到“全局经营决策”

行业现状与痛点：现有客服 Agent 只处理“单个工单”的问答，缺乏全局洞察。安克业务繁杂，单纯靠人工追踪海量 Bad Case 并反哺业务，几乎不可能。

我们的创新：推出面向商家的归因 Agent，处理的是“工单的集合”——自动将快照数据转化为带责任归属与规则 ID 的决策建议。

典型场景举例

案例 1 · 反哺产品设计：系统自动发现 X10 Pro 报错「3212（拖布阻塞）」的客诉激增，追溯至 Excel 具体行号，直接给产品部下达建议——「该批次高频出现故障，建议专项排查传感器设计」。

案例 2 · 反哺物流流程：系统发现多起「只收到配件、未收到主机」的客诉。归因分析指出是「拆单物流信息展示不清」导致，建议物流团队优化订单页面的包裹拆分展示逻辑。

系统级效果三个创新点强强联合形成数据飞轮，最终达到的系统级效果，就是抗幻觉。

2\.2 产品逻辑与技术架构#

产品逻辑与技术方案#

OntoCare 全链路技术架构与自进化机制：处理流程参考业界领先的 GraphRAG 思想，并结合安克售后场景做了深度的「本体化」改造。系统采用「图谱 \+ 向量」混合架构与严密的幻觉拦截机制，全链路分为六个步骤。

Step 1

##### 多模态输入与降维解析

用户发起求助时，支持文本或图片 / 视频输入。若是图片或视频，系统先调用多模态大模型 API，提取可见现象、型号线索、错误码及不确定项，转化为结构化文字描述。这段文字与用户原输入组合，作为精准的 Query 进入主链路。

多模态 API可见现象 / 型号线索 / 错误码不确定项标注Query 合成

Step 2

##### 自上而下的数据清洗与双本体图谱构建离线

我们不采用自下而上让模型盲目抽取的方式（那会带来极大的图谱噪声）。我们采用预先定义 Schema 框架的本体构建模式，由售后业务专家深度参与，梳理实体、关系与规则——前期虽有人工成本，但换来了极高的数据纯净度。同时结合 HyperAuto 自动化集成理念，将安克产品、订单、SOP 映射为 Service Ontology 和 Decision Ontology，存入图数据库与向量库。

预定义 Schema业务专家参与高数据纯净度HyperAuto 自动化集成图数据库 \+ 向量库

Step 3

##### 实体限定与「图谱 \+ 向量」混合召回

用户 Query 进入后先进行实体消歧，将检索范围死锁在唯一产品的知识子图内，随后执行混合召回：

##### 本体图谱 · 权威来源

依靠本体图谱完成图推理与业务决策（如查订单、定型号、匹配置信动作），这是结果可靠性的基石。

##### 向量检索 · 语义补充

仅作为辅助，用于在子图内召回长尾的 FAQ、SOP 文本素材。两者结合，兼顾了业务规则的确切性与自然语言的泛化性。

实体消歧死锁知识子图图推理 \+ 业务决策长尾 FAQ / SOP 语义召回

Step 4

##### 上下文组装、大模型生成与「二次拦截校验」

系统将召回的知识、用户 Query、本体节点关系以及 Allowed / Blocked Actions 组装进 Prompt，喂给核心的 DeepSeek LLM。生成回复后，系统绝不直接输出，而是叠加幻觉检测与校验环节：对 Agent 输出的业务结论、引用来源以及工具调用动作进行服务端二次拦截校验。一旦发现无依据承诺或越权，立即强制回退，多层次抑制大模型幻觉。

上下文组装DeepSeek LLM服务端二次拦截校验无依据承诺 / 越权 → 强制回退

Step 5

##### 用户反馈与 Bad Case 捕获

答案输出给用户后，界面提供点赞与点踩。一旦用户点踩，该条对话轨迹、检索来源、案件状态与 Decision Trace 会被立刻打包，自动打上 Bad Case 标签进入待排查队列。

点赞 / 点踩对话轨迹检索来源案件状态 \+ Decision TraceBad Case 标签

Step 6

##### 靶向归因与自进化闭环

针对捕获的 Bad Case，系统沿处理链路进行根因定位与靶向修复：

##### ① 长尾策略补充与安全兜底

如果是超出当前知识库覆盖的长尾问题，将修复经验补充进长尾策略库，并要求人工复核校验；若毫无可靠匹配，系统诚实追问或转人工。

##### ② 降噪剔除与规则更新

如果是常见问题，排查是否知识错误（降权剔除 / 修正 FAQ）或规则缺失（直接更新 Decision Ontology）。

##### ③ 引用校验与持续改进

新失败经人工审核修复后，加入回归测试集。后续在保持产品过滤的前提下，系统将持续评估引入 HyDE 与重排（Rerank）技术，让系统越用越聪明。

🧬

##### 「图谱 \+ 向量」混合架构 · 幻觉拦截机制

本体图谱负责权威决策，向量检索只做语义补充；生成后经服务端二次拦截校验，发现无依据承诺或越权立即强制回退。用户点踩即捕获 Bad Case，经根因定位、靶向修复与人工审核后回写知识库与双本体，形成越用越聪明的数据飞轮。

架构选型理由#

我们评估了四条可选路线，最终选择「轻量 Schema \+ 规则引擎 \+ 在线模型 API」，理由是：本赛题的关键变量是业务规则执行的确定性，而不是模型能力本身。

局限性与领先性#

局限性（客观边界）

领先性（确定性与友好性，降维打击）

相比于现有的传统 Workflow 或纯 RAG 方案，我们的方案具备极强的技术先进性与企业级复用价值：

01 · 业务敏捷的确定性

降维打击

突破传统 Workflow 的「牵一发而动全身」。业务变动只需在本体图谱中修改节点连线或属性，无需修改底层代码，实现了真正的业务敏捷。大模型负责模糊理解，确定性程序负责业务边界。

02 · 战略级全局资产

数字孪生底座

系统沉淀的是企业专属业务数字孪生知识图谱，统一了业务语义、数据标准与动作边界。它独立于大模型存在，不会被模型迭代或微调所同化，是可长期复用、跨部门传承的企业固有资产。

03 · 面向未来的多 Agent 协同

MCP 适配

依托统一的本体语义，系统能完美对齐未来所有智能体的上下文，原生适配 MCP 等上下文协议。随着业务拓展，长期演进仅需优化知识图谱，底层架构永久稳定，实现全域协同统一化。

赛道标注#

智能服务赛道（知识数据召回的策略是什么？图片信息如何处理？）

一

知识数据召回策略 · 先限定适用范围，再检索可用证据

从业务对象建模，到引用校验的五步链路

1

##### 数据结构化：基于本体论先建立业务对象和处理规则

将订单、客诉工单、经销商和两份 Q\&A 作为输入，保留来源文件、Sheet、原始行号及校验信息。知识条目依据发布状态和客户可见状态过滤，作为后续引用与核查的基础。

2

##### 先确认产品，再限定知识范围

结合用户描述、SKU、订单及对话状态定位产品。同名或冲突信息未澄清时，先展示候选选项；确认后按产品 PN 限定检索范围，减少跨型号知识混用。

3

##### 按问题类型召回

对错误码优先精确匹配；对一般现象使用关键词、同义词和相关度匹配，选取少量适用条目。条件明确的常见问题可命中带来源校验的固定 FAQ，减少重复生成。

4

##### 长尾策略补充与安全兜底

常见路径不能覆盖时，检索长尾策略和 Bad Case 修复经验，结合当前证据交给模型组织建议。补充策略与官方产品知识分别标识；没有可靠匹配时继续补充信息或人工核查。

5

##### 引用校验与持续改进

答复附带来源 ID，服务端检查引用有效性和部分业务一致性。新失败经人工审核修复后加入策略与回归测试。当前尚未使用向量检索；后续可在保持产品过滤与来源约束的前提下，评估语义召回、混合检索和重排。

逐层判断失败发生在哪一环，再对症修复；所有修复都必须经人工审核后回写知识库与双本体。

发现 Bad Case

Q1 · Query 超出业务边界？

是 → 诚实兜底追问补充信息，或转人工处理

Q2 · 检索召回正确知识？

否 → ③ 降噪剔除错误知识降权 / 剔除，修正 FAQ，长尾策略补全

Q3 · Decision Ontology 规则计算正确？

否 → ③ 更新决策本体修补前置条件，调整 Allowed / Blocked 边界

Q4 · LLM 生成合规且无幻觉？

否 → ② Judge 靶向纠偏强化引用校验，补充 Few\-shot 例子

✓ 正确生成 / 安全兜底

输出符合业务边界

④ 人工审核回流 · 写回双本体与知识库所有修复路径统一经人工审核，通过后更新知识库与 Ontology，并加入回归测试

二

图片与视频处理 · 先生成文字证据，再进入原有业务链路

多模态只做证据提取，不直接下结论

1

##### 多模态 API 转译

用户上传故障图片或视频后，系统调用多模态大模型 API，提取可见现象、型号线索、错误码及不确定项，生成结构化文字描述。

2

##### 生成检索 Query

将多模态提取的文字与用户原输入合并，作为新的 Query 注入业务检索链路，精准触发上述分层召回策略。

3

##### 证据状态绑定

识别结果不直接作为认定产品身份或质保资格的唯一凭证，而是强制标记为「待核验」（PROBABLE / UNKNOWN），参与后续与订单 SKU 的交叉核对，确保多模态处理的安全严谨。
