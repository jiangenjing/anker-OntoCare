# OntoCare 商业 BP：创新点核验与路演建议

核验日期：2026-10-17（北京时间）。依据当前代码及已保存评测记录。本次是证据审计，没有重新运行完整在线评测，也没有运行传统日志方案性能对照。

## 一、结论：三个方向成立，成熟度和措辞必须区分

| 原说法 | 核验结果 | 推荐写法 |
|---|---|---|
| 解决业务归因、提升复盘能力 | 已能聚合真实工单、生成RC候选、下钻证据和提出行动；未证明真实复盘效率提升，也未验证因果根因 | 把售后工单转化为可追溯的归因线索和待核查行动，辅助经营复盘 |
| 本体带来低时延、低成本，优于传统日志 | 代码具备预计算、固定FAQ和规则复用；缺少基线、计费和当前版本端到端测量 | 通过结构化关联、规则复用和FAQ缓存减少重复检索与模型生成；效果将在同条件对照中验证 |
| 自进化 | 已有Bad Case策略沉淀、检索、回归测试、待审核标记；主要靠人工/工程修改 | 人工审核驱动的Bad Case知识沉淀与回归改进机制 |
| LLM Judge + 红蓝对抗有效 | 模块已实现，动态在线样例可核验；未做消融证明优于普通评测 | 硬断言、LLM语义评审和红蓝追问结合，帮助发现并回归验证业务边界问题 |

“使用本体”本身是技术选择；更值得讲的差异是：实体关联、规则约束、证据引用、行动建议和评测回写如何共同服务业务。

## 二、代码证据与能力边界

### 1. 从客服问答走向经营复盘

- `dataset.py`：把产品、订单明细、工单、知识和经销商源数据关联，保留来源行号。
- `static/merchant-attribution-agent.js`：执行工单统计、RC候选条件、知识覆盖、建议动作和高管摘要生成。
- `reports/attribution_report.json`：看板与经营助手共用的归因快照。
- `analytics_assistant.py`：实际执行 ReadOntology 和 ReadTrace，读取产品、规则、归因审计，确定性计算数据后再请求模型生成建议。
- `scripts/merchant_attribution/assistant.html`：聊天、连续追问、证据链与原文点击。

当前RC3有两条关联工单候选，不是“已确认两个设计缺陷”。X10 Pro有14条工单，不意味着其故障率最高；缺少销量分母。RC4缺少完整投诉日期时不能判定过保临界。

当前的 ReadOntology、ReadTrace 是读取 JSON/内存关系及已有归因审计的函数，不是部署了通用图数据库或SPARQL查询引擎。实体关联与规则解释已存在，自动因果推断未被证明。

### 2. 低成本与低时延

- `qa_workflows.py + data/faq-cache.json`：命中明确适用条件时，可以使用固定答案减少生成调用。
- `conversation_workflow.py`：复用已经确认的信息和排障进度。
- `scripts/merchant_attribution/build.py`：在构建时完成聚合；静态看板读取已经生成的快照。
- 经营聊天仍会调用LLM；输入语义解析主要采用产品名/RC词匹配及上下文继承。

因此必须区分：静态看板渲染时间、本体/规则查询时间、知识检索时间、完整LLM回答时间、离线快照构建时间。缓存命中率、Token成本和分析效率也需要分别计量。

历史在线客服测得P50约2.63秒、P95约9.00秒，不含浏览器渲染；这是历史客服接口数据，不能改写为经营归因时延。历史P95还高于报告中8秒目标。业务约束页中的模拟成本或时延数字不能作为实测成绩。

不能直接说“本体一定比日志快”。日志可以被索引、结构化和缓存；公平比较应固定数据、模型、硬件、并发、输入长度和输出质量。

### 3. Bad Case持续改进

- `docs/knowledge/long_tail/评测修复策略库.md`：记录失败场景、槽位、边界和处理策略。
- `long_tail_knowledge.py`：启动时读取MD/JSON，检索候选策略；不是模型训练。
- `tests/`：验证修复场景与旧行为。
- `analytics_api.py`：保存知识缺口的审核状态；代码明确“审核通过不自动发布到正式知识库”。

已有流程：失败日志 → 人工定位与修复策略 → 修改代码/提示词/知识 → 回归测试 → 重新打包/重启生效。

仍待补齐的自动化：自动聚类去重、候选策略生成、证据审查、隔离验证、审批发布、版本回滚、发布后效果监测。BP可称“具备持续演进框架”，不能称“完全自主自进化”。

## 三、80%究竟是什么

| 指标 | 数值 | 真实口径 |
|---|---:|---|
| 历史在线核心硬断言通过率 | 62/74 = 83.8% | 核心任务首轮；非整体准确率 |
| 历史模型裁判主张忠实度 | 302/351 = 86.0% | 首轮可评轨迹中的主张；同模型裁判估计 |
| 历史语义目标达成估计 | 74/101 = 73.3% | 101条有有效裁判结果的轨迹 |
| 历史硬断言+裁判联合通过 | 69/101 = 68.3% | 两种条件共同满足；不能用83.8%替代 |
| 含不支持主张的轨迹比例 | 41/101 = 40.6% | 模型估计，非人工确认幻觉率；一条轨迹只要一个主张不支持即计入 |
| 后续修复回归核心通过率 | 73/74 = 98.6% | 在线首轮硬断言，110条中的109条整体通过 |
| 后续修复回归LLM Judge | 未测量 | 在线110条记录的judge状态均为NOT_MEASURED |
| 动态红蓝在线样例 | 1个案例、2轮 | U093，真实LLM红队与Judge；两轮faithfulness均为1.0，不能推广为全量成绩 |
| FCR、真实降本、商业复盘收益 | 未测量 | 需要重开记录、人力投入和真实业务观测 |

依据：`benchmark/benchmark-metrics.json`、`benchmark/benchmark-results.json`、`benchmark/repair-final-results.json`、`reports/红蓝对抗在线实测.json`。

后续修复结果只做一次独立试验，没有新的pass^3/pass^8；旧版八次通过率不能直接用于当前版本。83.8%与98.6%来自不同代码版本/运行配置，且评测器存在修订记录，不能直接宣称当前版本取得相同比例的净提升。

当前代码继续变化，历史成绩必须标记为历史版本。模型裁判与被测模型使用同一模型体系，存在相关偏差；它能补充硬断言，不能代替独立人工金标准。

### 评测本身的亮点

`benchmark/agents/red_team.py`负责Persona追问；`blue_team.py`调用真实客服接口；`judge.py`结合引用、产品范围、PII、动作约束检查与模型语义估计；`orchestrator/runner.py`汇总轨迹和终态；`chaos.py`注入故障。

历史主要成绩包含固定场景/固定输入评测，新增动态红队的小样例是另一实验。不能说所有历史83.8%结果都来自动态红蓝对抗。也没有证据证明“引入LLM Judge后，业务准确率自然提升”；Judge是发现问题的工具，改进来自修复及验证。

## 四、推荐的BP定位与问题叙事

### 一句话定位

OntoCare 是面向多SKU售后团队的本体驱动服务与经营复盘助手，将客户问题、产品知识、业务规则和核查行动连接为可追溯的证据链。

### 三个业务痛点（作为待试点验证的问题假设）

1. 多SKU、同名产品与拆单信息交织，客服容易关联错产品、重复索取信息。
2. 工单、知识和政策分散，复盘人员难以快速定位“哪些问题值得核查、依据是什么、谁来跟进”。
3. Bad Case反复出现，单次修复没有沉淀为可复用策略和回归样本。

不要直接宣称已证明安克全组织存在同样程度的问题；当前样本展示的是业务场景与处理难点，规模和收益需要企业访谈/试点验证。

### 对应的三个产品创新表述

1. 可追溯经营归因：从工单统计进一步连接规则、原文与待核查行动，让复盘结论可验证。
2. 规则与模型协同：明确边界用代码规则，稳定问题用缓存和工作流，复杂表达和建议用LLM。
3. 评测驱动的知识改进：通过硬断言、LLM Judge及红蓝追问发现问题，将经审核的修复沉淀为知识与回归测试。

低成本、低时延放在第二点的“设计目标与待验证收益”，不要在当前阶段作为已证明优于竞品的主结论。

## 五、五分钟路演建议：8页BP

| 页 | 用时 | 内容 | 演示或证据 |
|---|---:|---|---|
| 1 | 20秒 | 一句话定位：让售后从答复走向有证据的复盘 | 用户端→商家端→经营归因→评测四个入口 |
| 2 | 40秒 | 三个真实场景难点 | S1 Pro歧义、拆单、反复失败工单 |
| 3 | 40秒 | 方案架构：实体—规则—证据—行动 | 展示主干架构与字段关联 |
| 4 | 60秒 | 核心Demo：X10工单查询，再追问RC3核查 | 点击源表行号与规则定义；避免宣称根因已证实 |
| 5 | 40秒 | AI Native分工与持续改进 | 展示LLM用在哪里、规则约束在哪里、Bad Case如何沉淀 |
| 6 | 45秒 | 评测证据 | 83.8%硬断言、86.0%主张忠实度，分母和版本写清；补充缺陷与边界 |
| 7 | 35秒 | 落地与商业验证 | 先做单一售后团队试点；衡量复盘耗时、证据完整度、重开率及成本 |
| 8 | 20秒 | 需要的合作与下一阶段目标 | 获取试点数据、售后负责人、完整历史/销量与业务反馈 |

对应评分：第3/5页解释创新与AI作用；第2/4/7页证明场景价值；第4/6页展示完整度与边界；整段Demo保持和讲解同步。不能把评分权重转成自评成绩。

## 六、商业模式：当前适合写为验证方案

- 目标用户：售后运营、客服主管、产品质量/支持团队；采购与试点责任人需访谈确认。
- 交付形态：企业服务软件/集成方案，先接入工单和知识快照，后接真实CRM/订单身份权限。
- 收费假设：初始化知识与本体映射服务费 + 按团队/用量的订阅，具体价格待验证；当前代码没有付费闭环或收入证据。
- 价值指标：找到证据所需时间、人工复核耗时、归因建议采纳率、问题重开率、单位合格回答成本。
- 护城河假设：经审核的实体映射、业务规则、失败样本和回归资产持续积累；需要用覆盖率、复用率和跨SKU迁移结果验证，不能只说“有本体所以有壁垒”。

## 七、补证实验：支持下一版BP的最小方案

1. 对同批源表安排盲评复盘任务，对比“人工翻日志/原表”与“OntoCare辅助”；分别记录耗时、正确引用率、遗漏与误判。相同任务采用交叉顺序，避免记忆效应。
2. 机器侧比较：固定同一模型、硬件、并发、数据和质量门槛，比较普通检索流程与当前实体/规则流程；分冷/热缓存记录P50/P95、Token和真实费用。
3. 自进化验证：隔离开发用Bad Case和未见过的改写测试集；修复前后比较新增用例通过率与旧任务退化率，保留版本及审批记录。
4. Judge校准：抽取人工双标并处理分歧的样本，测模型裁判一致性和误判；单独记录模型不可用/无效输出，不计为通过。
5. 独立留出集：现有真实工单规模有限，避免把已用于提示词与规则修复的样本当作未见评测。

## 八、可直接用于BP的摘要

OntoCare面向多SKU售后场景，将产品、订单、知识和服务规则关联为可追溯的证据链。用户侧提供产品消歧、候选订单、知识支持和连续排障；商家侧把工单聚合为经营核查线索，并通过AI对话展示规则依据和原文。

系统采用规则、固定问答与LLM协同处理，形成“发现Bad Case—人工审核修复—沉淀策略—回归验证”的持续改进机制。历史在线核心硬断言通过率为62/74（83.8%）；模型裁判对351条主张的忠实度估计为302/351（86.0%）。后续硬断言回归73/74通过，该次未启用语义裁判，以上成绩需分别呈现。

当前已验证的是Demo中的实体关联、证据下钻、规则约束和模型建议能力。复盘效率、成本节约和跨产品迁移收益，将通过真实团队试点及同条件对照验证。
