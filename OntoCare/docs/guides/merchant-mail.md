# 商家邮件工作台：方案与验证

## 方案与落地

客户页保留四个初始问题，依据《客诉工单信息.xlsx》第 3、12、55、32 行改写；标明示例，不当作当前客户的实际订单。新增 /merchant 商家工作台，与客户聊天分开。

商家选择原表邮件或粘贴新邮件，选择中英文，生成可编辑的主题和正文，并复制草稿及引用。页面展示真实处理进度，以及邮件、产品、订单、质保渠道、已尝试操作、知识来源、动作范围的核对结果。

本体关系为：ServiceCase → Product / Order / Evidence → PolicyDecision → prepare_email_draft。沿用现有 Python 规则、订单资料、公开 Q&A 和缓存优先机制；不新增独立多 Agent 进程。

## 数据

读取原表 63 封首封邮件：11 封 Shipping inquiry、52 封 Troubleshooting/Product usage。原表有英、荷、法、德、西语内容；本版本输出语言为中英文，未宣称具备完整多语言意图理解。不能确认时使用澄清草稿。

data/mail-tickets.json 为原表离线快照。scripts/import_mail.py 可使用安装 openpyxl 的 Python 重新导入：python scripts/import_mail.py /完整路径/客诉工单信息.xlsx。导入后重启服务。原 Excel 不修改，附件链接不自动打开或下载。

## 规则

- 每封邮件使用独立临时案件，不继承客户聊天上下文，完成后清理。
- 原文完全一致才继承所选工单的 SKU/订单；编辑正文后重新识别，不沿用旧元数据。
- 安全问题优先于物流/故障/缓存；烫伤邮件不进入普通充电排障。
- 已尝试操作会被识别；充电触点已清洁的场景不重复建议清洁。
- 物流查询保留同订单所有包裹，不用一件配件的签收状态代表整单。
- 知识原文较长或不够确定时，作为商家复核资料，邮件仅询问补充信息。
- 草稿编号对应引用列表。客户陈述与知识/订单事实分开。引用链接为本地核对链接，对外使用前需替换为客户可访问链接。

## 验证

52 项测试通过；邮件遍历测试在禁用模型配置时处理全部 63 封原表邮件，验证草稿、流式进度、引用链接和临时案件清理。另覆盖分包物流、安全优先、已尝试操作、编辑邮件丢弃旧元数据、客户聊天隔离、中英文、非法输入、来源 HTML 转义、真实吸奶器邮件缓存命中与零模型调用。

浏览器实际验证初始问题、EB1L 草稿生成、引用显示及复制功能。自动化通过不等于逐封语义质量全部通过；未配置真实模型，因此未验证长尾模型的实际回复质量。

仅生成草稿，没有邮件发送接口，也没有退款、换货、维修、人工转接执行器。页面刷新不持久保存编辑后的草稿。本地演示无商家登录权限隔离，不用于直接公开部署。
