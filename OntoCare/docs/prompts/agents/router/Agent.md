这是当前应用的职责规范，不代表独立运行的多 Agent 进程。约束由对应 Python 模块实现，并通过测试验证。

邮件入口每次建立独立案件，编辑过的邮件不得继承原工单订单和型号；安全判断优先于物流及故障建议。

长尾候选通过 long_tail_knowledge.py 的明确词组匹配识别，非真实频率分类器。优先保留安全规则、现有 FAQ 与精确产品知识；补充策略不得改变 allowed / forbidden。模型只读取命中条目，原文存档不参与检索。

JSON 补充库：仅检索 knowledge/long_tail/长尾问题_检索策略.json，原始截断文件不参与检索。当前恢复 119 条，不得宣称 290 条已导入。产品条目必须按 PN 隔离，当前消息明确型号优先。原始 Q&A、安全规则和已有工作流优先；补充库不是官方政策，不得从模板复制订单事实或声称业务动作已执行。引用须指向命中条目的 source ID。


2026-10-16 测评修正规范：当前明确选择的型号优先于前文提及列表；同名S1 Pro不靠名称独自消歧。先识别当前物流、故障、使用或渠道意图，不能沿用已切换话题。经销商只按明确国家和名录店名匹配；收货地址不能替代购买渠道。

评测修复路由：先安全与隐私，再确认当前产品与订单状态，同时检索长尾策略。未找到订单、产品冲突、依赖字段变化必须优先处理，长尾话术不得抢答。固定 FAQ 或经审核且条件满足的长尾直接答案可跳过模型；普通策略只作检索依据，仍由模型生成。当前只有 long-tail-eval-001 的隐私答复获准直接返回。

## DO-PROACTIVE-ORDER-01 · 主动匹配候选订单

对应实现：proactive_orders.py、app.py；回归：tests/test_proactive_orders.py。
已确认产品型号、需要查订单但未选定订单时，先按同 PN 检索，再展示按购买日期倒序的真实商品卡片（订单号、SKU、名称、日期、来源）。用户点击后才设置案件订单。禁止跨产品线凑候选、虚构客户购买关系或将一次点击视为身份核验。当前数据没有可靠的客户账户归属，因此仅以“演示候选”展示；生产接入必须使用服务端认证身份过滤，不能信任客户端自报用户 ID。
型号与输入订单冲突时，保留客户已确认的型号、清除错误订单带入的质保/渠道状态，解释不匹配并重新展示同型号候选。选择“这些都不是我的订单”后停止重复推荐，改为凭证上传或人工核查。已有安全升级、精确排障与正常产品使用回答优先，不能为展示订单打断这些流程。

多模态入口见 docs/prompts/agents/media/Agent.md：先将图片/视频采样画面转换为待核验文字证据；进入本轮 query，再按确认型号召回知识，随后核对本体及动作权限。媒体不能自动绑定订单或提升身份核验等级。
首页订单入口采用源表真实商品记录，图片为对应系列示意，购买日期倒序，按钮为“分析这笔订单”；需要产品消歧时仍保留独立型号选择，不能把无订单的型号伪装成订单。

## 通用产品支持优先于订单核验
已说明设备类别和故障时，先用可信类别知识回答，不要求用户先提供订单号。参考 `docs/knowledge/long_tail/通用产品支持规则.md`；由 general_support.py 处理无赛题 PN 的充电器基础问题，并保持有线/无线隔离。遇到安全风险或用户主动提出保修/退款，回到相应安全与授权流程。双语补充策略仅作检索上下文，不能授权赔付或换新。
