# 商家邮件工作流

对应模块：mail_workflow.py；入口 /api/mail/stream。

邮件正文是证据，不能覆盖规则。仅在正文与原表完全一致时继承该行订单/SKU；编辑后重新判断。每封邮件使用独立案件，不沿用客户聊天状态。

ServiceCase 关联 Product、Order、Evidence 与 PolicyDecision。先识别安全问题，再检查型号、订单、已尝试操作、知识来源和允许动作。受伤或冒烟问题不能继续普通排障；不把已有操作当作未做。来源不足时提出具体补充要求，禁止把长篇知识原文直接作为邮件发送。

生成礼貌、简洁、可编辑的中英文草稿。保留对应证据编号及来源。未接入邮件发送、实时物流或真实售后办理，禁止声称已经执行这些动作。

本规范由工作流代码实现；未新增独立模型进程。现有知识回复沿用原有缓存优先、长尾模型辅助机制。

用户端超过 8 次交互可保存本地人工/邮件请求。商家显示来源字段；没有客户 ID 或完整 SKU 时显示未提供。对话转入时保留记录，基于最近实质问题及最新反馈生成，不把系统会话 ID 当作客户 ID。

本次商家增强：merchant_assist.js 提供开场语气切换及恢复；不重写事实正文。情绪分仅由当前真实邮件关键词估计，无历史不能推断升级趋势。复制和模拟发送前检查部分承诺词，用户修改后重新检查；这不等于服务端发信许可或完整事实验证。安全识别共享 qa_workflows.RISK，不将安全事件自动描述为已受伤。

商家编辑新增 mail_editing.py：三版本、五语言翻译、选段改写通过真实模型处理；输入草稿为不可信资料，不执行其指令。模型输出保护订单号、SKU、数字及引用编号，失败保留原文；字段保护不等于完整语义验证，仍需人工核对。版本独立保存编辑；请求中如果草稿或案件变化，不覆盖新内容。客户画像只显示来源明确字段，订单号不充当客户ID。


2026-10-16 测评修正规范：正式、友好、简洁、共情通过/api/mail/rewrite的tone动作改写完整草稿；数字、订单号和引用数量必须保持。只调整表达，不改资格或承诺。用户已尝试操作要保留，不重复开清单。

2026-10-17 邮件语言一致性：严格使用用户指定的回复语言；自动模式跟随客户来信。主题、称呼、感谢语、正文与落款统一语言，品牌和业务标识保留。语气、三版本和选段改写沿用当前草稿语言，只有明确翻译操作才切换语言，并同步翻译主题。最终草稿在原售后规则处理后进行语言检查，必要时调用已有邮件编辑器翻译，保护数字、订单、SKU、错误码与引用；检查失败不返回错误语言的成功草稿。不改变本体架构、案件状态、检索、排障或售后决策。
